현재 코드 베이스와 이번에 반영된 고도화 사항(특히 메모리와 에러 복구)을 기준으로 봤을 때, 테스트 도구를 쓰지 않고 수동으로 직접 디버깅(확인)해봐야 할 잠재적 리스크 영역은 다음과 같습니다.

🔍 현재 디버깅 및 점검이 필요한 사항 리스트
1. 대화 메모리 무한 증식 및 토큰 한도 초과 문제 (Token Overflow)

원인: MemorySaver를 적용하여 대화 내역을 계속 축적(operator.add)하고 있으나, 오래된 대화를 요약(Summary)하거나 잘라내는(Truncate) 로직이 현재 graph.py나 state.py에 없습니다.
디버깅 포인트: 사용자와의 대화 턴이 10~20회 이상 길어질 때, Gemini나 OpenAI 모델의 최대 입력 토큰 수를 초과해 ContextWindowExceeded 관련 에러가 발생하는지 확인해야 합니다.
2. 에러 자동 복구(Fallback)의 무한 루프 위험

원인: 도구 실행 중 에러가 발생하면 "다시 파라미터를 수정해서 호출해봐"라고 프롬프트로 유도했습니다.
디버깅 포인트: 만약 사용자가 애초에 불가능한(혹은 너무 모호한) 정보를 요구해 LLM이 계속 찍어 맞추기를 시도할 경우, Agent ↔ Tool 사이를 무한히 오가며 무한 루프에 빠지는지 테스트해야 합니다. (LangGraph의 recursion_limit이 기본적으로 잡아주긴 하지만, 에러 메시지 폭주 현상이 없는지 봐야 합니다)
3. Streamlit 화면 데이터와 LangGraph 메모리 상태 불일치 (State Sync)

원인: 화면 표시는 st.session_state.messages에 수동으로 .append() 하고 있고, 에이전트 내부의 기억은 MemorySaver에 별도로 축적됩니다.
디버깅 포인트: 스트림릿 앱을 새로고침 시 화면의 대화기록(st.session_state.messages)은 날아가지만 LangGraph의 thread_id가 고정("streamlit_session")되어 있어, 에이전트는 이전 대화를 기억하고 있는 '유체이탈' 현상이 발생하는지 확인이 필요합니다.
4. 상대적 날짜(동적 컨텍스트) 포맷 정밀도

원인: current_time을 시스템 시간으로 넘겨주고 LLM이 알아서 "다음주 수요일"을 YYYY-MM-DD로 바꾸게 했습니다.
디버깅 포인트: 달이 넘어가는 시점(예: 4월 30일 다음 날)이나 윤년 등을 LLM이 단순 텍스트 추론 중에 오계산해서 DB(SQLite)나 캘린더에 기입하지 않는지 디버깅이 필요합니다.
5. RAG 조회 시 캘린더/과제 연계 복합 질문 한계치

원인: 14개 툴이 병렬로 열려 있습니다.
디버깅 포인트: "학사 공지에서 수강신청 기간 찾아서 통째로 일정이랑 과제 일정에 넣어줘" 라고 요청했을 때, LLM이 search_notices를 한 뒤 획득한 텍스트에서 날짜를 파싱해 다시 add_calendar_event와 add_task를 순차적으로 온전히 완료하는지 확인해야 합니다.
