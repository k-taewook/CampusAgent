# CampusAgent 12주차 보완 계획

작성일: 2026-05-26  
대상 기간: 2026-05-20 ~ 2026-05-27  
작성 기준 문서: `md_file/plan.md`, 현재 `mcp_servers/student_info_server.py`, `rag/external_crawler.py`, `agent/prompts.py` 구현 상태.

## 1. 12주차 방향 변경

12주차에는 원래 계획했던 Multi-Agent 구조 개발을 새로 진행하지 않는다.

대신 기존 프로그램을 최종 발표와 최종보고서에 사용할 수 있도록 보완한다.
특히 공공 API나 공공 웹사이트 크롤링 결과가 사용자의 실제 상황과 맞지 않는 정보를 많이 가져오는 문제를 점검하고, 해결 가능한 범위와 한계를 정리한다.

이번 주의 핵심 질문은 다음과 같다.

- 사용자가 "내가 받을 수 있는 청년 정책을 찾아줘."라고 했을 때 왜 이상한 정책이 섞이는가.
- 이 문제를 코드 수정으로 어느 정도 해결할 수 있는가.
- 완전히 해결하기 어렵다면 발표와 보고서에서 어떤 한계로 설명해야 하는가.

## 2. 현재 문제 판단

결론부터 말하면, 이 문제는 **부분적으로는 해결 가능하지만 완전히 자동 해결하기는 어렵다**.

개선 가능한 부분은 검색어 처리, 결과 필터링, 출처 분리, 사용자 조건 확인, 응답 방식이다.
하지만 "내가 받을 수 있는 정책"을 정확히 판정하려면 정책별 신청 자격과 사용자의 개인정보가 모두 필요하다.
현재 프로그램은 전공, 학년, 관심 영역, 희망 진로 정도를 주로 사용하고 있어서 청년 정책 자격 판정에 필요한 정보가 부족하다.

청년 정책 추천에 필요한 대표 조건은 다음과 같다.

- 나이 또는 생년월일.
- 거주 지역.
- 학교 재학 여부와 학년.
- 취업 상태.
- 소득 구간 또는 가구 조건.
- 사업자 여부.
- 관심 분야.
- 신청 가능 기간.

이 정보가 없으면 시스템은 "받을 수 있는 정책"이 아니라 "관련 있어 보이는 정책 후보"만 추천할 수 있다.
따라서 12주차 목표는 완전한 자격 판정 시스템을 만드는 것이 아니라, 이상한 결과를 줄이고 사용자가 원문에서 확인할 수 있게 만드는 것이다.

## 3. 현재 구현에서 이상한 결과가 생기는 원인

### 3.1 공공 API 검색이 제목 중심으로 동작한다.

`rag/external_crawler.py`의 `fetch_youth_policy()`는 온통청년 API에 `plcyNm` 검색어를 전달한다.
이 방식은 정책 제목 중심 검색에 가깝다.
사용자가 "내가 받을 수 있는 청년 정책"처럼 넓게 물으면 정책 자격 조건을 충분히 반영하지 못한다.

현재 결과에는 정책명, 간단한 설명, 기관, URL 정도가 들어간다.
하지만 나이, 지역, 취업 상태, 소득 조건 같은 자격 필드가 구조화되어 비교되지 않는다.

### 3.2 사용자 프로필이 정책 자격 판정에 부족하다.

`agent/prompts.py`에는 전공, 학년, 개인화 프로필이 들어간다.
하지만 청년 정책 추천에 중요한 거주 지역, 나이, 소득, 취업 상태는 기본 프로필에 없다.

따라서 "내가 받을 수 있는"이라는 표현을 엄밀하게 처리하기 어렵다.
현재 구조에서는 사용자가 조건을 따로 알려주지 않으면 시스템이 추측할 수밖에 없다.

### 3.3 학교 공지 크롤링과 공공 정책 검색의 목적이 섞일 수 있다.

`search_student_info_live()`는 학교 대표 홈페이지 공지를 카테고리 키워드로 크롤링한다.
예를 들어 정책 카테고리에서는 `국가장학금`, `장학금`, `국가근로` 같은 키워드를 사용한다.

이 방식은 학교 공지 검색에는 유용하지만, 전국 청년 정책 검색과는 성격이 다르다.
사용자가 청년 정책을 물었는데 학교 공지, 장학 공지, 과거 저장 데이터가 함께 검색되면 결과가 어색해질 수 있다.

### 3.4 검색 결과가 ChromaDB에 누적되면서 잡음이 쌓일 수 있다.

외부 결과는 `_store_external_results()`를 통해 ChromaDB에 저장된다.
이후 `search_student_info()`가 저장된 샘플과 과거 크롤링 결과를 함께 검색한다.

한 번 부정확하거나 범위가 넓은 결과가 저장되면 다음 검색에서도 다시 나타날 수 있다.
이 구조는 캐시처럼 편리하지만, 검색 품질이 낮은 데이터가 누적될 위험이 있다.

### 3.5 LLM이 "후보"를 "확정 추천"처럼 말할 수 있다.

도구 결과 자체는 원문 확인을 안내하지만, 최종 응답에서 LLM이 정책을 확정적으로 추천하면 사용자가 실제로 받을 수 있다고 오해할 수 있다.
정책 정보는 신청 조건이 자주 바뀌기 때문에 응답은 항상 "후보", "확인 필요", "원문 기준"으로 표현해야 한다.

## 4. 해결 가능 범위

### 4.1 바로 개선 가능한 항목

다음 항목은 12주차 보완 작업으로 충분히 개선 가능하다.

- "내가 받을 수 있는"이라는 질문이 들어오면 바로 검색하지 않고 필요한 조건을 먼저 물어본다.
- 사용자 조건이 없을 때는 "정확한 자격 판정은 어렵고 후보 검색만 가능하다."고 안내한다.
- 온통청년 API 결과를 그대로 보여주지 않고 지역, 나이, 재학 여부, 취업 상태 같은 키워드로 2차 필터링한다.
- 결과마다 "왜 관련 있다고 판단했는지"와 "확인해야 할 조건"을 함께 표시한다.
- 학교 공지 검색 결과와 공공 정책 API 결과를 응답에서 명확히 분리한다.
- 검색 점수가 낮거나 조건 정보가 부족한 결과는 하단의 "참고 후보"로 낮춰 보여준다.
- ChromaDB에 저장할 때 외부 공공 API 결과와 학교 공지 결과를 더 명확한 metadata로 구분한다.

### 4.2 구현은 가능하지만 시간이 더 필요한 항목

다음 항목은 구현할 수 있지만 12주차 발표 준비 일정에서는 범위를 조절해야 한다.

- 사용자 설정 탭에 나이, 거주 지역, 취업 상태, 소득 구간 입력 항목 추가.
- 온통청년 API의 세부 필드를 더 많이 파싱해서 자격 조건 테이블로 구조화.
- 정책별 신청 가능 여부를 `가능`, `조건 확인 필요`, `대상 아님`으로 분류.
- 검색 결과 품질 평가 테스트 데이터셋 작성.
- 공공 API 결과 전용 ChromaDB 컬렉션 분리.

### 4.3 완전히 해결하기 어려운 항목

다음 항목은 현재 프로젝트 범위에서 완전 해결이 어렵다.

- 모든 청년 정책의 실제 신청 가능 여부를 자동 확정하는 것.
- 소득, 가구, 거주, 고용 상태처럼 민감하거나 변동되는 조건을 사용자가 입력하지 않았는데 정확히 추론하는 것.
- 공공 API 원자료가 누락되었거나 오래된 경우 이를 자동으로 보정하는 것.
- 정책 원문과 공고 PDF의 세부 예외 조건까지 모두 안정적으로 해석하는 것.

따라서 최종 발표에서는 이 기능을 "청년 정책 후보 탐색과 원문 확인 보조"로 설명하는 것이 안전하다.
"사용자가 받을 수 있는 정책을 확정 판정한다."고 설명하면 실제 구현 범위보다 과장된다.

## 5. 12주차 보완 목표

12주차 보완 목표는 다음과 같다.

1. 청년 정책 검색 결과가 이상하게 나오는 원인을 정리한다.
2. 사용자 조건이 부족할 때 확인 질문을 먼저 하도록 프롬프트를 보완한다.
3. 공공 API 결과를 후보로 표현하고, 확정 추천처럼 보이지 않게 응답 문구를 조정한다.
4. 검색 결과에 출처, 신청 기간, 대상 조건 확인 필요 여부를 더 명확히 표시한다.
5. 구현이 어려운 부분은 최종보고서의 한계점과 향후 개선 방향으로 정리한다.

## 6. 권장 구현 계획

### 6.1 프롬프트 보완

`agent/prompts.py`의 대학생 정보 검색 안내에 다음 규칙을 추가한다.

- 사용자가 "내가 받을 수 있는", "나한테 맞는", "신청 가능한" 청년 정책을 요청하면 나이, 거주 지역, 재학 여부, 취업 상태를 먼저 확인한다.
- 사용자가 조건을 이미 말한 경우에만 `search_scholarship_policy`를 호출한다.
- 결과는 "신청 가능 확정"이 아니라 "조건상 확인해볼 후보"로 표현한다.
- 정책 추천 후에는 반드시 원문 URL 확인을 안내한다.

이 변경은 코드 구조를 크게 바꾸지 않고도 오해를 줄일 수 있다.

### 6.2 정책 검색 도구 응답 개선

`mcp_servers/student_info_server.py`의 `search_scholarship_policy()` 응답을 다음처럼 바꾼다.

- 헤더를 `관련 청년정책/장학금 후보`로 표현한다.
- 각 항목에 `확인 필요 조건` 문구를 추가한다.
- 결과가 넓게 잡힐 수 있다는 안내를 footer에 추가한다.

예시 응답 방향은 다음과 같다.

```text
🏛️ '청년 주거 지원' 관련 청년정책 후보.

이 결과는 신청 가능 확정이 아니라 조건 확인이 필요한 후보입니다.
나이, 거주 지역, 소득, 취업 상태에 따라 실제 신청 가능 여부가 달라질 수 있습니다.
```

### 6.3 사용자 조건 기반 2차 필터링 추가

가능하면 `search_scholarship_policy()`에 선택 인자를 추가한다.

```python
def search_scholarship_policy(
    query: str,
    n_results: int = 5,
    region: str = "",
    age: str = "",
    employment_status: str = "",
    student_status: str = "",
) -> str:
    ...
```

12주차 최소 구현에서는 API 요청 자체를 복잡하게 바꾸기보다, 받아온 결과의 title/content/source에 사용자 조건 키워드가 포함되는지 확인해 점수를 조정하는 방식이 현실적이다.

예를 들어 사용자가 `인천`, `대학생`, `미취업`을 말했으면 해당 단어가 포함된 결과를 위로 올린다.
조건이 전혀 맞지 않는 결과는 제외하거나 "참고 후보"로 낮춘다.

### 6.4 저장 데이터 오염 줄이기

공공 API 검색 결과를 ChromaDB에 저장할 때 metadata를 더 명확히 한다.

권장 metadata는 다음과 같다.

- `source_type`: `public_api`, `school_notice`, `sample`.
- `provider`: `youthcenter`, `worknet`, `school_homepage`.
- `eligibility_checked`: `false`.
- `query_context`: 사용자가 입력한 원 질문.

12주차에 컬렉션 분리까지 하지 않더라도 metadata를 분명히 하면 이후 검색과 보고서 설명이 쉬워진다.

### 6.5 검색 결과 분리 표시

최종 응답에서는 결과를 다음처럼 분리한다.

- 조건이 비교적 맞는 후보.
- 조건 확인이 필요한 후보.
- 관련성은 낮지만 참고할 수 있는 후보.

이렇게 나누면 이상한 정보가 일부 섞여도 사용자가 결과의 신뢰도를 구분할 수 있다.

## 7. 12주차 최소 작업 범위

발표와 최종보고서 준비를 고려하면 12주차 최소 작업은 다음으로 제한한다.

- `agent/prompts.py`에 청년 정책 검색 전 확인 질문 규칙 추가.
- `search_scholarship_policy()` 응답 문구를 후보 추천 중심으로 수정.
- 정책 결과 footer에 자격 조건 확인 필요 문구 추가.
- `week_12_plan.md`와 최종보고서에 한계와 개선 방향 정리.

이 범위는 짧은 시간 안에 사용자 오해를 줄이고 발표에서도 설명하기 좋다.

---

## 8. 12주차 선택 작업

시간이 남으면 다음을 추가한다.

- `search_scholarship_policy()`에 `region`, `age`, `employment_status`, `student_status` 선택 인자 추가.
- 조건 키워드 기반 간단한 rerank 함수 추가.
- `tests/test_student_info.py`에 조건 부족 안내와 API 키 없음 테스트 보강.
- 공공 API 결과 metadata에 `source_type`과 `eligibility_checked` 추가.

이 작업까지 하면 "품질 개선을 실제 코드로 일부 반영했다."고 말할 수 있다.

## 9. 검증 계획

자동 테스트 후보는 다음과 같다.

```powershell
python -m pytest tests/test_student_info.py -q
python -m pytest tests/test_agent.py -q
```

수동 검증 질문은 다음과 같다.

```text
내가 받을 수 있는 청년 정책 찾아줘.
```

기대 동작은 바로 정책을 확정 추천하지 않고, 나이와 지역 등 필요한 조건을 먼저 묻는 것이다.

조건을 포함한 검증 질문은 다음과 같다.

```text
나는 인천에 사는 대학생이고 아직 취업 안 했어. 내가 받을 수 있는 청년 정책 찾아줘.
```

기대 동작은 관련 정책 후보를 보여주되, 실제 신청 가능 여부는 원문에서 확인해야 한다고 안내하는 것이다.

## 10. 최종보고서에 쓸 판단

최종보고서에는 다음처럼 정리한다.

CampusAgent의 청년 정책 검색 기능은 공공 API와 공식 웹사이트를 활용해 사용자의 관심사와 관련된 정책 후보를 찾는 기능이다.
하지만 정책의 실제 신청 가능 여부는 나이, 거주 지역, 소득, 취업 상태, 재학 상태, 신청 기간 등 다양한 조건에 따라 달라진다.
현재 시스템은 이 조건을 모두 구조화해서 판정하지 않으므로, 결과를 확정 추천이 아니라 후보 추천으로 제공한다.

따라서 본 프로젝트에서는 청년 정책 검색을 "원문 확인을 돕는 탐색 기능"으로 정의한다.
향후 개선 방향은 사용자 프로필 항목 확장, 정책 자격 조건 구조화, 공공 API 결과 전용 저장소 분리, 조건 기반 reranking 도입이다.

---

## 11. 12주차 완료 기준

- [ ] 청년 정책 검색 결과가 이상하게 나오는 원인을 문서화한다.
- [ ] 완전 해결이 어려운 이유를 사용자 조건 부족과 공공 데이터 한계로 구분해 정리한다.
- [ ] 12주차 최소 보완 작업 범위를 정한다.
- [ ] 최종 발표에서 이 기능을 과장하지 않고 설명할 수 있는 문구를 준비한다.
- [ ] 가능하면 프롬프트와 응답 문구를 수정해 "확정 추천" 오해를 줄인다.

---

## 12. 요약

공공 API와 공공 웹사이트 기반 검색이 이상한 정보를 가져오는 문제는 단순한 버그 하나로 보기 어렵다.
검색어가 넓고, 사용자 조건이 부족하며, 공공 데이터의 자격 조건이 완전히 구조화되어 있지 않기 때문이다.

따라서 12주차에는 이 기능을 무리하게 완전 자동 추천으로 확장하지 않는다.
대신 사용자 조건 확인, 후보 표현, 출처 확인 안내, 결과 분리 표시를 통해 실제 사용자가 덜 헷갈리도록 보완한다.
